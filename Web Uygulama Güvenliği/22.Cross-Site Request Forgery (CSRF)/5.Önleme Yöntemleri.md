CSRF, ciddi sonuçları olabilen bir zafiyet olsa da, doğru stratejilerle etkili bir şekilde önlenebilir. Modern web uygulamalarında CSRF'yi önlemek için birden fazla savunma katmanı kullanmak en iyi yaklaşımdır.

### 1. Anti-CSRF Token'ları (Synchronizer Token Pattern)

En yaygın ve en güvenilir yöntemlerden biri, **Anti-CSRF Token** kullanmaktır. Bu yöntemde, sunucu her kullanıcı oturumu için benzersiz ve tahmin edilemez bir token oluşturur. Bu token, kullanıcının yaptığı her durum değiştirici istekte (örn: form gönderimi) sunucuya geri gönderilmelidir.

**Nasıl Çalışır?**

1. **Token Oluşturma:** Kullanıcı oturum açtığında veya durum değiştirecek bir sayfayı (örn: profil ayarları) ziyaret ettiğinde, sunucu kriptografik olarak güvenli, rastgele bir token oluşturur ve bunu kullanıcının oturum bilgileriyle ilişkilendirerek sunucu tarafında saklar.
2. **Token'ı İstemciye Gönderme:** Sunucu, bu token'ı istemciye gönderir. Token, genellikle formun içinde gizli bir 
    
    input
    
     alanı (
    
    <input type="hidden">
    
    ) olarak yerleştirilir.
3. **Token'ı Doğrulama:** Kullanıcı formu gönderdiğinde, bu gizli token da istekle birlikte sunucuya gönderilir. Sunucu, istekle gelen token ile kullanıcının oturumu için sakladığı token'ı karşılaştırır.
    - Eğer token'lar eşleşirse, istek gerçektir ve işleme alınır.
    - Eğer token'lar eşleşmezse veya istekte token yoksa, istek reddedilir.

Saldırgan, başka bir siteden sahte bir istek gönderdiğinde, bu gizli token'ın değerini bilemez. Bu nedenle, sunucuya göndereceği istek geçersiz olur.

PHP'de Güvenli Kod Örneği

secure_change_email.php

```auto
<?php
session_start();

// Kullanıcının oturumu yoksa yönlendir
if (!isset($_SESSION['user_id'])) {
    header('Location: /login.php');
    exit();
}

// --- GÜVENLİ KISIM ---

// 1. Token Oluşturma ve Doğrulama
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    // Formdan gelen token ile session'daki token'ı karşılaştır
    if (!isset($_POST['csrf_token']) || !hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
        // Token'lar eşleşmiyorsa, isteği reddet
        die('Geçersiz CSRF Token!');
    }

    // Token doğrulandı, işlemi gerçekleştir
    $new_email = $_POST['email'];
    echo "E-posta adresiniz başarıyla güncellendi: " . htmlspecialchars($new_email);
    // Başarılı işlem sonrası yeni bir token oluşturmak iyi bir pratiktir.
    unset($_SESSION['csrf_token']);

} else {
    // Sayfa ilk yüklendiğinde (GET isteği), yeni bir token oluştur ve session'a kaydet
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
}
?>

<!-- Güvenli E-posta Değiştirme Formu -->
<form method="POST" action="secure_change_email.php">
    <label for="email">Yeni E-posta Adresiniz:</label>
    <input type="email" id="email" name="email">

    <!-- 2. Token'ı forma gizli bir alan olarak ekle -->
    <input type="hidden" name="csrf_token" value="<?php echo htmlspecialchars($_SESSION['csrf_token']); ?>">

    <button type="submit">Güncelle</button>
</form>
```

**Not:**

hash_equals()

fonksiyonu, zamanlama saldırılarına (timing attacks) karşı koruma sağlamak için iki string'i güvenli bir şekilde karşılaştırır.

Yukarıdaki form gönderildiğinde, tarayıcının oluşturacağı HTTP isteği şu şekilde olacaktır:

Token İçeren Güvenli HTTP İsteği

```auto
POST /secure_change_email.php HTTP/1.1
Host: your-site.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 99
Cookie: session=...

email=new.email@example.com&csrf_token=a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2
```

Gördüğünüz gibi,

csrf_token

değeri form verileriyle birlikte gönderilir. Sunucu bu değeri, kullanıcının oturumunda saklanan değerle karşılaştırarak isteğin gerçekliğini doğrular.

Modern JavaScript Uygulamalarında (AJAX/SPA) Kullanım

Single Page Application (SPA) gibi modern yapılarda, form gönderimleri yerine genellikle arka plana AJAX istekleri (örn:

fetch

veya

axios

ile) yapılır. Bu durumda token'ı göndermek için farklı bir yaklaşım kullanılır.

1. **Token'ı Meta Etiketinde Saklama:** Sunucu, ana sayfa yüklendiğinde token'ı bir HTML meta etiketine yerleştirir.
    
    ```auto
    <meta name="csrf-token" content="a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2">
    ```
    
2. **Token'ı Başlığa Ekleme:** İstemci tarafındaki JavaScript kodu, bu meta etiketinden token'ı okur ve yapacağı her AJAX isteğine özel bir HTTP başlığı (
    
    X-CSRF-TOKEN
    
    gibi) olarak ekler.
    
    ```auto
    const csrfToken = document.querySelector('meta[name="csrf-token"]').getAttribute('content');
    
    fetch('/api/update-profile', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-CSRF-TOKEN': csrfToken
      },
      body: JSON.stringify({ email: 'new.email@example.com' })
    });
    ```
    

Bu yöntemle, her istekte token'ı manuel olarak formlara eklemek gerekmez. JavaScript kütüphaneleri veya framework'ler (örn: Laravel, Django, Ruby on Rails) genellikle bu süreci otomatikleştirir. Sunucu tarafı, gelen isteklerde

X-CSRF-TOKEN

başlığını kontrol edecek şekilde yapılandırılır.

### 2. SameSite Cookie Attribute'u

SameSite

cookie attribute'u, tarayıcılara bir cookie'nin siteler arası (cross-site) isteklerle birlikte gönderilip gönderilmeyeceğini bildiren güçlü bir mekanizmadır. Bu, CSRF saldırılarına karşı tarayıcı düzeyinde bir koruma sağlar.

SameSite

üç değere sahip olabilir:

- Strict
    
    : Cookie, yalnızca cookie'nin ait olduğu siteden yapılan isteklerle gönderilir. Başka bir siteden (örn: bir linke tıklayarak) hedef siteye gelindiğinde bile cookie gönderilmez. Bu en güvenli ayardır ancak kullanıcı deneyimini olumsuz etkileyebilir.
- Lax
    
    : 
    
    Strict
    
    'e benzer, ancak kullanıcı başka bir siteden bir linke tıklayarak hedef siteye gittiğinde (üst düzey navigasyon) cookie'nin gönderilmesine izin verir. Form gönderimleri (POST), 
    
    <img>
    
     veya 
    
    <iframe>
    
     gibi isteklerde cookie gönderilmez. Bu, çoğu uygulama için güvenlik ve kullanılabilirlik arasında iyi bir denge sunar. Modern tarayıcıların varsayılan ayarı genellikle 
    
    Lax
    
    'tır.
- None
    
    : Cookie, tüm siteler arası isteklerle birlikte gönderilir. Bu ayar kullanılırken, cookie'nin 
    
    Secure
    
     attribute'ünün de (yani sadece HTTPS üzerinden gönderim) ayarlanması zorunludur.

**Örnek:**

HTTP Response Header

```auto
Set-Cookie: session=AbC1dE2fGh...; SameSite=Lax; HttpOnly; Secure
```

### 3. Referer Başlığı Doğrulaması

Sunucu, gelen bir isteğin

Referer

HTTP başlığını kontrol ederek isteğin kendi kaynağından mı yoksa başka bir siteden mi geldiğini anlayabilir. Eğer

Referer

başlığı beklenmedik bir domaine aitse, istek reddedilebilir.

**Ancak bu yöntem tek başına güvenilir değildir, çünkü:**

- Bazı kullanıcılar veya güvenlik yazılımları, gizlilik nedeniyle 
    
    Referer
    
     başlığını tarayıcı isteklerinden kaldırabilir. Bu durum, gerçek kullanıcıların engellenmesine neden olabilir.
- Referer
    
     başlığı bazen manipüle edilebilir.

Bu nedenle,

Referer

kontrolü genellikle Anti-CSRF token'larına ek olarak ikincil bir savunma katmanı olarak kullanılır.
