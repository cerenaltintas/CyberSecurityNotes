Server-Side Template Injection (SSTI) zafiyetini tespit etmek, sistematik bir yaklaşım gerektirir. Süreç, genellikle basit bir matematiksel işlem içeren bir payload enjekte ederek sunucunun bu ifadeyi işleyip işlemediğini kontrol etmekle başlar. Eğer sunucu, gönderilen ifadeyi matematiksel olarak çalıştırıp sonucunu yanıtta döndürüyorsa, bu durum SSTI zafiyetinin varlığına dair güçlü bir işarettir.

### Adım 1: Zafiyetin Tespiti

SSTI'yi tespit etmenin en güvenilir yolu, şablon sözdiziminde kullanılan özel karakterleri (

$

,

{

,

}

,

%

,

<

,

>

) içeren bir payload göndererek uygulamanın nasıl tepki verdiğini gözlemlemektir.

Örneğin, bir web sitesinde

?name=kullanici

parametresi olduğunu varsayalım.

**Normal HTTP İsteği:** Kullanıcı,

name

parametresine normal bir değer gönderir.

Request

```auto
GET /profile?name=Jules HTTP/1.1
Host: vulnerable-site.com
...
```

**Normal HTTP Yanıtı:** Sunucu, bu değeri doğrudan sayfaya yazar.

Response

```auto
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
...

<h1>Hoş Geldin, Jules!</h1>
```

Şimdi, aynı parametreye basit bir matematiksel işlem içeren bir payload gönderelim. Popüler şablon motorlarından Jinja2'nin sözdizimini (

{{ ... }}

) kullanalım.

**Payload'lı HTTP İsteği:**

name

parametresine

{{7*7}}

payload'ını enjekte ediyoruz.

Request

```auto
GET /profile?name={{7*7}} HTTP/1.1
Host: vulnerable-site.com
...
```

Bu isteğe verilebilecek üç olası yanıt vardır:

**Yanıt 1: Zafiyet Yok (No Vulnerability)** Uygulama, girdiyi düz metin olarak işler ve hiçbir değerlendirme yapmaz. Bu, en yaygın ve güvenli senaryodur.

Response

```auto
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
...

<h1>Hoş Geldin, {{7*7}}!</h1>
```

**Yanıt 2: Zafiyet Yok - Girdi Temizlenmiş (Sanitized)** Uygulama, potansiyel olarak tehlikeli karakterleri (

{

,

}

) kaldırır veya HTML entity'lerine dönüştürür.

Response

```auto
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
...

<h1>Hoş Geldin, 7*7!</h1>
<!-- veya -->
<h1>Hoş Geldin, &lcub;&lcub;7*7&rcub;&rcub;!</h1>
```

**Yanıt 3: Zafiyet Onaylandı (Vulnerability Confirmed)** Uygulama, şablon motoru aracılığıyla girdiyi işler ve

7*7

işleminin sonucunu yanıta yazar. **Bu, SSTI zafiyetinin varlığını doğrular.**

Response

```auto
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
...

<h1>Hoş Geldin, 49!</h1>
```

Eğer yanıt olarak

49

gibi bir sonuç alıyorsak, sunucunun bir şablon motoru kullandığını ve gönderdiğimiz girdiyi işlediğini kesin olarak söyleyebiliriz.

### Adım 2: Template Motorunu Tanımlama

Zafiyeti tespit ettikten sonraki en önemli adım, hangi şablon motorunun kullanıldığını belirlemektir. Çünkü her motorun kendi sözdizimi ve sömürü tekniği vardır. Bu süreç, genellikle deneme-yanılma yoluyla, farklı motorlara özgü payload'lar gönderilerek yapılır.

Aşağıdaki akış şeması ve tablo, bu süreçte size yardımcı olabilir.

**Tanımlama için Akış Şeması (Metin Tabanlı):**

1. {{7*7}}
    
     gönder. Yanıt 
    
    49
    
     ise, muhtemelen Twig veya Jinja2'dir. Yanıt 
    
    {{7*7}}
    
     ise, Adım 2'ye geç.
2. ${7*7}
    
     gönder. Yanıt 
    
    49
    
     ise, muhtemelen Freemarker'dır. Yanıt 
    
    ${7*7}
    
     ise, Adım 3'e geç.
3. <%= 7*7 %>
    
     gönder. Yanıt 
    
    49
    
     ise, muhtemelen Ruby (ERB) tabanlıdır.
4. Diğer motorlara özgü payload'ları dene.

**Motor Tanımlama için Payload Tablosu:**

|Payload|Beklenen Sonuç|Potansiyel Motor(lar)|
|---|---|---|
|{{7*'7'}}|49|Twig|
|{{7*'7'}}|7777777|Jinja2|
|{{'a'.toUpperCase()}}|A|Jinja2 (Mako, Twig, Nunjucks)|
|${7*7}|49|Freemarker|
|<#assign x="7*7">${x}|49|Freemarker|
|@{7*7}|49|Razor (.NET)|
|@(7*7)|49|Razor (.NET)|
|#{7*7}|49|Java (JSF)|
|*{{7*7}}*|*49*|Handlebars|
|{{ this.getClass() }}|Java nesnesi adı|Java (Genel)|
|<%= 7 * 7 %>|49|Ruby (ERB)|

**Örnek: Jinja2 Tespiti** Aşağıdaki payload'ı gönderdiğimizi varsayalım:

Request

```auto
GET /profile?name={{7*'7'}} HTTP/1.1
Host: vulnerable-site.com
...
```

**Yanıt (Jinja2):** Jinja2, string çarpmasını karakter tekrarı olarak yorumlar.

Response

```auto
HTTP/1.1 200 OK
...

<h1>Hoş Geldin, 7777777!</h1>
```

Bu yanıt, motorun büyük olasılıkla Jinja2 (veya benzeri bir Python motoru) olduğunu gösterir. Eğer motor Twig olsaydı, bu isteğe bir hata (error) ile yanıt verirdi çünkü Twig string ile integer arasında çarpma işlemine izin vermez.

### SSTI Zafiyeti Nerelerde Aranmalı?

SSTI zafiyetleri, kullanıcı girdisinin sunucu tarafında bir şablona dahil edildiği her yerde bulunabilir. Yaygın olarak kontrol edilmesi gereken yerler şunlardır:

- **URL Parametreleri:** 
    
    GET
    
     isteklerindeki sorgu dizileri (
    
    ?param=değer
    
    ).
- **POST Verileri:** Formlar aracılığıyla gönderilen veriler (
    
    username
    
    , 
    
    comment
    
    , 
    
    search
    
     alanları).
- **HTTP Başlıkları (Headers):** 
    
    User-Agent
    
    , 
    
    Referer
    
    , 
    
    X-Forwarded-For
    
     gibi başlıklar, loglama veya analiz için işleniyor olabilir.
- **Çerezler (Cookies):** Özellikle 
    
    welcome_message
    
     gibi kişiselleştirme için kullanılan çerez değerleri.
- **Dosya Yükleme:** Yüklenen dosya adları, şablonlanmış bir "başarıyla yüklendi" mesajında kullanılabilir.
- **E-posta Şablonları:** Pazarlama veya bildirim sistemlerinde kullanıcıların e-posta şablonlarını düzenlemesine izin veren özellikler.
- **CMS ve Wiki Sayfaları:** İçerik yönetim sistemlerinde veya wiki'lerde sayfa içeriği veya makro düzenleme.
